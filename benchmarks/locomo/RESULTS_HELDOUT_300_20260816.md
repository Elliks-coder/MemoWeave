## 6. 主要改进方向（不针对特定 case）

### 6.1 Multi-hop：优先改“证据覆盖”，不是继续降阈值

Multi-hop 的 Hit@5 为 81.67%，但 Recall@5 只有 40.14%，Accuracy 38.33%。这说明经常能找到至少一条相关证据，却不能找全组成答案的多条证据。

建议：

1. 对问题做实体/子问题分解，并行检索各子问题。
2. 重排目标从单条相关性改为“相关性 + 新证据覆盖”，避免 Top-K 被同一事件的同义记忆占满。
3. 以 provenance 的 session/turn 覆盖度做 MMR 或 set-cover 式选择。
4. 在答案阶段显式列出各子结论及其来源，再合成最终答案。

### 6.2 Temporal：召回已较高，推理/答案利用不足

Temporal Recall@5 为 76.94%，但 Accuracy 只有 55.00%；即使 Recall@5=1，时间题也只答对 29/44（65.91%）。

建议增加通用的结构化时间求解层：优先读取 `observed_at/event_start/event_end/temporal_relation/valid_from/valid_until`，完成日期锚定、先后排序和区间运算后，再让模型用自然语言回答。不要只把时间字段混在长文本上下文中。

### 6.3 Open-domain：允许受控常识推断，但保留高风险边界

Open-domain Accuracy 为 53.85%。在 9 道 Recall@5=1 的题里只答对 3 道；6 道失败中有 4 道直接回答“不知道”。说明之前放宽提示词仍未充分解决“证据已到但模型不敢推断”。

建议允许以下低风险、可验证的受控推断：城市→州/国家、行为描述→常见职业角色、明确属性→上位类别；同时要求回答标注“由记忆直接给出”还是“基于常识推断”。医疗、法律、财务等高风险结论仍应保持谨慎，不能为了 LoCoMo 分数强行诊断。

### 6.4 System 2：控制输出规模并保证原子性

`conv-47` 证明单次 JSON 输出会因 schema 过多打满 4096 tokens。建议采用以下任一通用方案：

1. 提示词限制每次最多生成 N 个高价值 schema/edge；
2. 分 cluster 调用并逐批原子提交；
3. 为 JSON 操作使用结构化输出，并在 `finish_reason=length` 时自动续写/重试；
4. 只有所有操作解析、执行和只读核验通过，digest 才标记成功。

### 6.5 返回上限与可观测性

应分别公开 `profile_limit/proactive_limit/normal_limit/total_limit`，并在 fallback 合并后再次裁剪。最终报告还应记录每路阈值前后候选数、重排前后排名和 fallback 原因，便于解释 Recall 与 Accuracy 的差距。
